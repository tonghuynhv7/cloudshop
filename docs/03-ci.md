# Phase 3 — GitHub Actions CI

## 🎯 Mục tiêu

Mục tiêu của phase này là tự động kiểm tra CloudShop mỗi khi code thay đổi.

Thay vì developer phải tự chạy:

```text
npm install
↓
syntax check
↓
docker compose up
↓
test /health
↓
test /ready
```

GitHub Actions sẽ tự động thực hiện các bước này.

Flow:

```text
Developer
    ↓
git push / pull request
    ↓
GitHub
    ↓
GitHub Actions
    ↓
CI Pipeline
    ↓
PASS / FAIL
```

---

# 1. CI là gì?

CI = Continuous Integration.

Ý tưởng chính:

```text
Code thay đổi
     ↓
Tự động kiểm tra
     ↓
Phát hiện lỗi sớm
```

Ví dụ developer tạo feature:

```text
feature/login
     ↓
Pull Request
     ↓
CI
   /    \
PASS    FAIL
 │        │
 ▼        ▼
Merge    Fix
```

CI đóng vai trò như một automated quality gate trước khi code được merge.

---

# 2. Workflow File

CloudShop sử dụng:

```text
.github/
└── workflows/
    └── ci.yml
```

GitHub Actions tự động tìm workflow trong:

```text
.github/workflows/
```

Cấu trúc cơ bản:

```yaml
name: CloudShop CI

on:
  ...

jobs:
  test:
    ...

  build-and-push:
    ...
```

Có thể hình dung:

```text
Workflow
│
├── Trigger
│
└── Jobs
     ├── test
     └── build-and-push
```

---

# 3. Workflow Trigger

CloudShop CI chạy khi:

```yaml
on:
  push:
    branches:
      - main

  pull_request:
    branches:
      - main
```

Có hai trường hợp.

## Push main

```text
Developer
    ↓
git push
    ↓
main
    ↓
GitHub Actions
```

## Pull Request vào main

```text
Feature Branch
      ↓
Pull Request
      ↓
main
      ↓
GitHub Actions
```

---

# 4. Tại sao cần Pull Request CI?

Giả sử đang làm:

```text
main
 │
 └── feature/cache
```

Developer thay đổi code trên:

```text
feature/cache
```

Thay vì merge ngay:

```text
feature/cache
      ↓
Pull Request
      ↓
CI Test
```

Nếu:

```text
CI PASS
```

thì code đủ điều kiện kỹ thuật để cân nhắc merge.

Nếu:

```text
CI FAIL
```

thì sửa code trước.

Flow:

```text
Feature
   ↓
PR
   ↓
CI
  / \
PASS FAIL
 │    │
 ▼    ▼
Merge Fix
```

Mục tiêu:

```text
Không để code lỗi đi vào main.
```

---

# 5. Job là gì?

Trong workflow:

```yaml
jobs:
  test:
```

`test` là một job.

Một workflow có thể có nhiều job:

```text
Workflow
│
├── test
├── build
├── security-scan
└── deploy
```

CloudShop hiện có flow:

```text
test
 ↓
build-and-push
```

---

# 6. Runner là gì?

Job cần một máy để chạy command.

CloudShop sử dụng:

```yaml
runs-on: ubuntu-latest
```

GitHub tạo một runner environment để thực thi job.

Tư duy:

```text
GitHub Actions
      ↓
Create Runner
      ↓
Ubuntu Environment
      ↓
Run Steps
```

Ví dụ:

```text
Runner
│
├── git checkout
├── Node.js
├── npm
├── Docker
└── curl
```

Sau khi job kết thúc, runner không nên được xem như server production lâu dài.

---

# 7. Job và Step

Một job gồm nhiều step.

Ví dụ:

```yaml
steps:
  - name: Checkout repository

  - name: Setup Node.js

  - name: Install dependencies

  - name: Verify application syntax
```

Tư duy:

```text
JOB
 │
 ├── Step 1
 ├── Step 2
 ├── Step 3
 └── Step 4
```

Các step trong cùng job chạy tuần tự theo thứ tự khai báo, trừ khi workflow có logic đặc biệt.

---

# 8. Checkout Repository

```yaml
- name: Checkout repository
  uses: actions/checkout@v4
```

Runner ban đầu không nên được hiểu là tự có source code CloudShop.

Ta cần:

```text
GitHub Repository
       ↓
Checkout
       ↓
Runner
       ↓
CloudShop Source Code
```

Sau bước này runner mới có:

```text
Dockerfile
compose.yaml
package.json
src/
nginx/
...
```

# 9. Setup Node.js

```yaml
- name: Setup Node.js
  uses: actions/setup-node@v4
  with:
    node-version: "20"
```

Mục đích:

```text
Runner
  ↓
Node.js 20
  ↓
CloudShop environment
```

Điều này giúp CI sử dụng Node.js version được xác định rõ.

# 10. Install Dependencies

CloudShop sử dụng:

```yaml

  run: npm ci
```

Tại sao dùng:

```text
npm ci
```

thay vì:

```text
npm install
```

Trong CI, ta muốn dependency installation dựa trên lock file và có tính lặp lại cao.

```text
package-lock.json
       ↓
npm ci
       ↓
Dependencies
```

Tư duy:

```text
CI
↓
reproducible dependency installation
```

# 11. Syntax Check

```yaml
- name: Verify application syntax
```

Mục đích:

```text

   ↓

 ▼            ▼
```

Đây là validation nhanh trước khi build toàn bộ stack.

# 12. Docker Compose Integration Test

CloudShop không chỉ kiểm tra JavaScript syntax.

CI còn chạy toàn bộ local architecture:

```yaml
- name: Build and start Docker Compose stack
  run: docker compose up -d --build
```

GitHub Runner tạo:

```text
Nginx
  ↓
API
 ├── PostgreSQL
 └── Redis
```

Điều này giúp kiểm tra các service có thực sự hoạt động cùng nhau hay không.

# 13. Tại sao syntax check chưa đủ?

Giả sử:

```text
server.js syntax ✅
```

nhưng:

```text
API không kết nối PostgreSQL ❌
```

hoặc:

```text
Nginx config sai ❌
```

Syntax check có thể vẫn pass.

Vì vậy CloudShop còn chạy:

```text
Docker Compose
      ↓
Full Stack
      ↓
Integration Test
```

# 15. Readiness Loop

CloudShop cần chờ application sẵn sàng trước khi test.

Ví dụ:

```yaml
- name: Wait for CloudShop readiness
  run: |
    for i in {1..20}; do
      if curl -fsS http://localhost/api/ready; then
        echo "CloudShop is ready"
        exit 0
      fi

      echo "Waiting for CloudShop... attempt $i/20"
      sleep 3
    done

    echo "CloudShop failed to become ready"
    docker compose ps
    docker compose logs
    exit 1
```

---

# 16. Tại sao cần chờ readiness?

Sau:

```bash
docker compose up -d --build
```

không có nghĩa application lập tức sẵn sàng.

Có thể:

```text
Container started
      ↓
PostgreSQL initializing
      ↓
Redis starting
      ↓
API connecting
      ↓
Application ready
```

Nếu CI test ngay:

```text
docker compose up
      ↓
curl ngay
      ↓
API chưa ready
      ↓
FAIL
```

Đây có thể là false failure do timing.

Vì vậy:

```text
Start Stack
    ↓
Wait
    ↓
Check /ready
    ↓
Ready?
 /       \
YES       NO
 │         │
 ▼         ▼
Continue  retry
```

---

# 17. Hiểu vòng `for`

```bash
for i in {1..20}; do
```

nghĩa là thử tối đa 20 lần.

Mỗi lần fail:

```bash
sleep 3
```

chờ 3 giây.

Tư duy gần đúng:

```text
Attempt 1
   ↓ fail
wait 3s

Attempt 2
   ↓ fail
wait 3s

...

Attempt 20
```

Nếu vẫn chưa ready:

```bash
exit 1
```

Job thất bại.

---

# 18. `curl -fsS`

CloudShop dùng:

```bash
curl -fsS http://localhost/api/ready
```

Các option quan trọng:

```text
-f
= fail khi HTTP response báo lỗi

-s
= silent

-S
= vẫn hiển thị error khi có lỗi
```

Trong CI, điều quan trọng là command trả exit code thất bại khi endpoint không đạt yêu cầu.

# 21. Logs khi thất bại

CloudShop sử dụng:

```yaml
- name: Show logs on failure
  if: failure()
  run: docker compose logs
```

`failure()` có nghĩa:

```text
Previous step failed?
       │
       ├── YES → show logs
       └── NO  → skip
```

Điều này rất hữu ích để debug CI.

Thay vì chỉ thấy:

```text
curl failed
```

ta còn có:

```text
PostgreSQL logs
Redis logs
API logs
Nginx logs
```

---

# 22. Cleanup

CloudShop sử dụng:

```yaml
- name: Cleanup
  if: always()
  run: docker compose down -v
```

`always()` nghĩa là chạy dù job trước đó:

```text
PASS
```

hay:

```text
FAIL
```

Flow:

```text
Tests
 /   \
PASS FAIL
 \   /
  \ /
Cleanup
```

---

# 23. `failure()` vs `always()`

Cần phân biệt:

```text
failure()
= chỉ chạy khi có failure

always()
= luôn chạy
```

CloudShop:

```text
Test
  ↓
Fail?
  ↓ YES
Show Logs

sau đó

Cleanup
= luôn chạy
```

---

# 24. `needs`

Job build/push sử dụng:

```yaml
needs: test
```

Nghĩa là:

```text
test
 ↓
PASS
 ↓
build-and-push
```

Nếu:

```text
test ❌
```

thì:

```text
build-and-push
```

không tiếp tục theo dependency thông thường.

Đây là quality gate:

```text
Bad Code
   ↓
CI FAIL
   ↓
không tạo artifact để delivery
```

---

# 25. Pull Request vs Push Main

Đây là logic rất quan trọng của CloudShop.

## Pull Request

```text
Feature Branch
      ↓
PR → main
      ↓
CI Test
      ↓
PASS / FAIL
      ↓
STOP
```

Mục tiêu:

```text
Validate code trước merge
```

## Push Main

```text
main
 ↓
CI Test
 ↓
PASS
 ↓
Build and Push Artifact
```

Mục tiêu:

```text
Validated code
      ↓
Create versioned artifact
```

---

# 26. Điều kiện Build & Push

CloudShop sử dụng logic:

```yaml
if: github.event_name == 'push' && github.ref == 'refs/heads/main'
```

Tách ra:

```text
github.event_name == 'push'
```

nghĩa là event phải là push.

Và:

```text
github.ref == 'refs/heads/main'
```

nghĩa là branch phải là main.

Cả hai phải đúng:

```text
PUSH?
  │
 YES
  │
MAIN?
  │
 YES
  ▼
build-and-push
```

Giả sử developer tạo:


PR có thể được sửa rất nhiều lần.

Nếu mỗi lần PR đều push production artifact:

```text
PR update
 ↓
ECR

PR update
 ↓
ECR

PR update
 ↓
ECR
```

sẽ tạo artifact không cần thiết và làm ranh giới giữa validation và delivery kém rõ ràng.

CloudShop sử dụng:

```text
PR
↓
Validate

Main
↓
Validate
↓
Build Artifact
```

# 28. Job chạy trên Runner riêng

Một khái niệm quan trọng:

```text
Job A
↓
Runner A

Job B
↓
Runner B
```

Không nên mặc định rằng filesystem, process hay credential của Job A sẽ tự tồn tại trong Job B.

Ví dụ:

```text
test
 ↓
Runner A

build-and-push
 ↓
Runner B
```

Vì vậy job `build-and-push` cần checkout source code lại.

```yaml
- uses: actions/checkout@v4
```

Và sau này nó cũng cần authenticate AWS trong chính job đó.

# 29. Tư duy Debug CI

Nếu pipeline fail, xác định step đầu tiên fail.

```text
Checkout?
   ↓
Node Setup?
   ↓
npm ci?
   ↓
Syntax?
   ↓
Docker Build?
   ↓
Containers Healthy?
   ↓
Readiness?
   ↓
Health?
```

Ví dụ:

```text
npm ci FAIL
```

thì chưa cần debug Nginx.

Nếu:

```text
Docker Compose build PASS
API unhealthy
```

thì kiểm tra:

```bash
docker compose logs api
```

Nếu:

```text
/ready FAIL
```

kiểm tra dependency:

```text
API
├── PostgreSQL?
└── Redis?
```

Tư duy:

```text
Find first broken link
        ↓
Debug that layer
```

Không sửa toàn bộ pipeline cùng lúc.

# 📌 CloudShop CI Flow

```text
                    GitHub Event
                         │
              ┌──────────┴──────────┐
              │                     │
             PR                 Push Main
              │                     │
              └──────────┬──────────┘
                         ▼
                       TEST
                         │
               ┌─────────┴─────────┐
               │                   │
              FAIL                PASS
               │                   │
               ▼                   ▼
              STOP           Main Push?
                                /   \
                              NO     YES
                              │       │
                              ▼       ▼
                             STOP   Continue
                                     ↓
                              build-and-push
```


1. PR
   → kiểm tra code trước khi merge

2. CI
   → không chỉ syntax
   → chạy cả Docker Compose stack

3. /ready
   → đợi application thực sự sẵn sàng

4. needs: test
   → test fail thì không được đi tiếp
